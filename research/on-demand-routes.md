# What on-demand routes cost the current static setup (issue #56)

Researched 2026-10-20 from the repo, developers.cloudflare.com, docs.astro.build, and a throwaway experiment. This records options, trade-offs, and gotchas; it does not pick one.

## Method and the one experiment

Claims about Astro and Cloudflare come from the docs pages cited inline. Claims marked **(verified)** come from an experiment on a scratch copy of `main` (not committed anywhere): `pnpm add @astrojs/cloudflare` (resolved 14.4.1; peer deps `astro ^7.4.0`, `wrangler ^4.125.0`, both met by `package.json`), `adapter: cloudflare()` added, one `export const prerender = false` endpoint at `src/pages/api/hello.ts`, then `pnpm build`, the repo's checks, and `wrangler dev`.

## Current setup, as the files say

- Astro 7 static output, no adapter; "Server rendering, if ever needed, is an additive change (`@astrojs/cloudflare`), not a rewrite" (`docs/adr/0001-astro-react-tailwind-static.md`).
- `wrangler.jsonc`: no `main`, so a pure static-assets Worker; `assets.directory: "./dist"`, `not_found_handling: "404-page"`, `compatibility_date: "2026-10-20"`, `previews: {}`, a `custom_domain` route for the apex, `workers_dev` and `preview_urls` on.
- CSP is built by Astro (`security.csp`, hashes in a per-page `<meta>`), then `scripts/csp-headers.mjs` (an `astro:build:done` hook) merges every page's policy plus `is:inline` script hashes into one `Content-Security-Policy` line under `/*` in `dist/_headers` and strips the meta tags. It throws if the line exceeds 2000 characters (Cloudflare drops longer `_headers` lines).
- Every other header (HSTS, nosniff, Referrer-Policy, Permissions-Policy, the `/_astro/*` immutable cache) also lives in `public/_headers`.
- CI (`.github/workflows/ci.yml`, one `check` job): prettier, eslint, `astro check`, `astro build`, `check:csp` (static scan of `dist`), `check:csp:runtime` (Playwright against `pnpm serve` = `wrangler dev --port 8788 --compatibility-date 2026-01-01`, paths `/` and `/404`, both themes), lychee on `dist/**/*.html`, then `pnpm lighthouse` (light config: 3 runs, 95/100/100/100 plus `csp-xss` and `errors-in-console`; dark config: accessibility 100 only; both on `/` and `/404`).
- Deploy (#18): Workers Builds on push to `main` (`npx wrangler deploy`), Previews for other branches, noindex added when `WORKERS_CI_BRANCH !== "main"` (`src/lib/build.ts`). A ruleset with no bypass keeps failing commits off `main`.

## Key fact that shapes every option

`_headers` applies only to static asset responses: "Custom headers defined in the `_headers` file are not applied to responses generated by your Worker code, even if the request URL matches a rule defined in `_headers`" (https://developers.cloudflare.com/workers/static-assets/headers/). **(verified)** In the experiment, `GET /` carried HSTS, nosniff, and the CSP from `_headers`; `GET /api/hello` carried only `Content-Type` and `Content-Length`. So any on-demand response needs its security headers set in code, and the single-source `public/_headers` stops being the whole story.

## Option A: `@astrojs/cloudflare` with mostly prerendered pages

How it works (https://docs.astro.build/en/guides/integrations-guide/cloudflare/, https://docs.astro.build/en/guides/on-demand-rendering/):

- Keep `output: "static"`, add `adapter: cloudflare()`, and mark each dynamic page or endpoint `export const prerender = false`. Everything else stays prerendered.
- The adapter sets `main` to `@astrojs/cloudflare/entrypoints/server`; an `assets` block "is no longer needed". The Cloudflare deploy guide says `astro add cloudflare` creates the config.
- Request flow is asset-first: a matching static asset is served and the Worker is not invoked; the Worker runs only when no asset matches (Cloudflare "worker-script" routing page). So prerendered pages stay free and unlimited (see Limits).

Build and deploy effects **(verified)**:

- Output splits into `dist/client` (static files, `_headers`, `404.html`, sitemap) and `dist/server` (`entry.mjs`, a generated `wrangler.json`). The build writes `.wrangler/deploy/config.json` pointing `wrangler deploy` at `dist/server/wrangler.json`, so the Workers Builds deploy command from #18 should keep working unchanged (the deploy itself was not run). `.wrangler/` is already gitignored.
- The generated config copied the repo's `name`, `routes`, `workers_dev`, `preview_urls`, `observability`, and `assets.not_found_handling: "404-page"` (so the custom 404 survives), set `assets.directory: "../client"` and `assets.binding: "ASSETS"`, and added `kv_namespaces: [{"binding":"SESSION"}]` and `images: {"binding":"IMAGES"}` (also under `previews`). The `SESSION` KV is provisioned on deploy; `session: false` in the Astro config skips it and keeps the session runtime out of the bundle. The default `imageService` is now `cloudflare-binding`; `compile` restores build-time optimization only.
- The prerender step runs in workerd. With the repo's `compatibility_date: "2026-10-20"` the build failed: "This Worker requires compatibility date 2026-10-20, but the newest date supported by this server binary is 2026-10-19." That is the same reason `pnpm serve` passes `--compatibility-date 2026-01-01`. With the adapter, `pnpm build` itself (locally and in CI) depends on the installed workerd supporting the config date. Lowering the date in `wrangler.jsonc`, or tracking wrangler upgrades, is the cost.
- A warning appeared: "Unexpected fields found in observability field: issue_detection" (wrangler 4.151.1 pinned in `package.json`; newer is 4.151.3). Whether it matters for deploy was not tested.
- `prerenderEnvironment` defaults to `workerd`; set `'node'` only if prerendered pages need Node APIs.

Bindings and types:

- Declare in `wrangler.jsonc` (`d1_databases`, `kv_namespaces`, `ai: {binding}`); read in code with `import { env } from "cloudflare:workers"` (v13+ removed `Astro.locals.runtime`). `astro:env/server` also works for vars.
- Types: run `wrangler types` after config changes; the adapter page suggests chaining it in `dev`, `build`, and `preview` scripts. Wrangler docs add that `wrangler types` no longer reads secret names from `.dev.vars`; list them in `secrets.required`.
- Auto-provisioning: omitting `id` lets wrangler create KV/D1/R2 on deploy, named with the Worker name as prefix. Caveat in the docs: when deploying from the dashboard or GitHub (Workers Builds), generated IDs are not written back to the repo. The D1 section still lists `database_id` as required; not reconciled in the docs read. AI needs no ID.

Local dev and Preview:

- `astro dev` and `astro preview` run in workerd via Cloudflare's Vite plugin; CommonJS deps may need `optimizeDeps.include`. Bindings default to local simulations; Workers AI always runs remotely (no local simulation) and is billed even in local dev (https://developers.cloudflare.com/workers/development-testing/, wrangler configuration page). `remote: true` on a binding makes calls hit the real resource, including writes.
- Previews do not inherit production settings: each Preview has "its own variables, secrets, and bindings" defined in the `previews` block, and KV/D1/R2 are isolated only if bound to separate resources (https://developers.cloudflare.com/workers/previews/). The repo already has `"previews": {}` with a comment that Previews inherit assets and compatibility settings; bindings are a separate matter. The adapter-generated config duplicates `SESSION` and `IMAGES` into `previews`. Preview URLs are public; workers.dev Preview URLs send `X-Robots-Tag: noindex` (so the repo's own noindex is belt-and-braces). Free plan: 100 Previews per Worker. AI binding behavior in Previews is not addressed by the page.
- Workers Builds env `WORKERS_CI_BRANCH` still drives `isProduction`; endpoints can import the same helper.

### Gotchas specific to this repo's gates (all **(verified)** unless noted)

1. `pnpm check:csp` fails: `ENOENT: open 'dist/_headers'`. It defaults to `dist`; output is now `dist/client`. `node scripts/check-csp.mjs dist/client` passes ("CSP covers every inline script and style in 2 pages"). The `astro:build:done` hook itself kept working because it receives the client directory.
2. The lychee step uses `--root-dir .../dist 'dist/**/*.html'`; with the split, root-relative links resolve against the wrong root unless the root-dir and glob move to `dist/client` (not run in the experiment; inferred from the path change).
3. `wrangler dev` (what `pnpm serve` runs) did serve the adapter build: `/` returned `_headers` headers and the static CSP, `/nope` returned 404 with the custom page, `/api/hello` returned 200 with no security headers. `check:csp:runtime` and Lighthouse only visit `/` and `/404`, so no gate would notice a dynamic route missing HSTS, nosniff, or CSP. New routes need their own paths in `paths` (`check-csp-runtime.mjs`) and `url` (both `lighthouserc` files).
4. Dynamic pages and the hash-based CSP: Astro's `security.csp` emits a `<meta>` per page; the docs say nothing on-demand-specific beyond that, and "Due to the nature of the Vite dev server, this feature isn't supported while working in `dev` mode" (Astro configuration reference). The repo's hook only post-processes `.html` files in the build output, and on-demand pages have no file there. So on-demand HTML pages would either keep Astro's meta tag (which cannot carry `frame-ancestors`, the stated reason the hook exists) or get no policy at all, and would get no `_headers` CSP. Whether the meta is emitted for on-demand pages in Astro 7 was not tested; the runtime `Astro.csp.insertDirective/insertScriptHash/insertStyleHash` API (`kind` option since 7.1) exists per page. A JSON/API endpoint has no HTML, but still needs a response-header policy if one is wanted (`default-src 'none'; frame-ancestors 'none'` is the usual shape).
5. Free-plan `_headers` limits still apply to the static half: 100 rules, 2000 characters per line. The merged CSP line is already length-guarded by `csp-headers.mjs`.
6. An on-demand page used as a Lighthouse target would add Worker CPU time and variance to the 3-run median performance score (assumption, not measured).
7. Prettier, eslint, `astro check`: not exercised. `astro check` will want `Env` types from `wrangler types`; not tested.
8. Dependabot's weekly grouped updates (#18) now cover `@astrojs/cloudflare`, whose peer range is tied to `astro` majors (v13 for Astro 6, v14 for Astro 7); ADR 0001 already lists Astro major upgrades as a recurring cost.

### Server islands

- `server:defer` on a component renders the page with a placeholder (`slot="fallback"`), then fetches the island from a special endpoint (`/_server-islands/...`) and swaps it in. Requires an adapter; each island is its own on-demand route, so the host page can stay prerendered (https://docs.astro.build/en/guides/server-islands/).
- Props are encrypted into a GET query string (so ordinary `Cache-Control` applies); above 2048 bytes it falls back to POST, which browsers don't cache. The encryption key is random per build; for CDN-cached pages or rolling deploys set `ASTRO_KEY` (`astro create-key`).
- Inside an island `Astro.url` is the internal path; use the Referer for page context. Prerendered pages can't read query params in the island.
- CSP interaction: the docs page does not discuss CSP. The host page needs an inline bootstrap script (whether Astro hashes it into the meta that the repo's hook merges is unverified), and the island fetch is same-origin so `connect-src` falls back to `default-src 'self'`, which the current policy allows. The island response itself is a Worker response, so the `_headers` caveat applies to it. Not tested: the experiment had no server island.
- Cost to the gates: each page with a server island adds a client-side fetch after load, which affects Lighthouse performance (layout shift from the fallback swap) and the `networkidle` wait in `check:csp:runtime`. Not measured.

## Option B: a separate Worker

- Keep the portfolio Worker exactly as is (no adapter, no `main`); put dynamic code in a second Worker with its own `wrangler.jsonc`, repo directory or repo, and its own Workers Builds connection (the Worker name in the dashboard must match the config `name`, per the earlier research on #8).
- Reaching it from the site: (a) a subdomain such as `api.cdprice.dev` as a second Custom Domain (cross-origin from the page: needs CORS and `connect-src https://api.cdprice.dev` in the CSP, which means touching `security.csp.directives` in `astro.config.mjs`); (b) a Route like `cdprice.dev/api/*` on the same hostname. Cloudflare's routes page says Routes take precedence over Custom Domains on the same hostname and gives an example of a route Worker in front of a Custom Domain app (https://developers.cloudflare.com/workers/configuration/routing/routes/); a route cannot be the target of a same-zone `fetch()`. Same-origin keeps `connect-src 'self'`. Not tested on this account.
- Static side impact: none. `dist/`, `check:csp`, lychee, Lighthouse, and the Workers Builds deploy command stay as they are; the static Worker's invocation count is unaffected.
- Costs: two deploy units, two Preview stories (service-binding calls from a Preview "go to the bound Worker's production deployment", so a static Preview would not exercise a Preview of the API Worker without wiring), a second place for bindings and type generation, and a second CI check (the current `check` job knows nothing about it).
- Free-plan accounting is per account: the 100,000 requests/day budget is shared by all Workers on the account, so a second Worker does not add headroom.
- Dynamic responses still need headers set in code (same caveat), but no hash pipeline is involved if it returns JSON.

## Option C: a Worker entry in front of the assets (`run_worker_first`)

- Add `main` and an `assets.binding` (e.g. `ASSETS`) to the existing `wrangler.jsonc`, keep `directory: "./dist"` and `not_found_handling`, and set `run_worker_first` to `true` or an array of patterns (https://developers.cloudflare.com/workers/static-assets/routing/worker-script/). With an array such as `["/api/*"]`, only matching paths invoke the Worker; the rest stay asset-first. Negative patterns starting with `!/` "continue to serve assets correctly" without invoking the Worker (billing and limitations page).
- The Worker calls `env.ASSETS.fetch(request)` to serve static files, and may transform the response (the docs' example uses `HTMLRewriter`). This is the only option here that lets one Worker both rewrite static responses and add routes, without Astro on-demand rendering. It also means the Worker could add headers to static pages, at the price of invoking the Worker for them.
- The Astro build stays static: no adapter, no `dist/client` split, `check:csp`, lychee, and the existing `_headers` flow are unchanged. Wrangler bundles the Worker `main` itself at `wrangler deploy`; `astro build` does not touch it, and `astro check` would not type it unless it is included in `tsconfig`.
- Billing: "requests matching the specified patterns will always invoke your Worker script." On the free plan, once the daily limit is exceeded those matched requests get a 429 rather than falling back. With `run_worker_first: true`, every page view consumes the 100,000/day budget and the static site stops serving when exceeded; with a narrow array only matched routes do.
- Known limitations: Smart Placement does not work correctly with `run_worker_first` (the whole Worker is placed as one unit). With Cloudflare Access, the Worker does not receive `ctx.access`.
- `_headers`: still ignored on Worker-generated responses; responses passed through `ASSETS.fetch` unmodified are asset responses and presumably keep their `_headers` headers (assumption, not verified).
- `check:csp:runtime` and Lighthouse already run through `wrangler dev`, so a `run_worker_first` Worker would run under those gates; only the new paths need adding to them. Not tested.

## Comparison for this repo

| Concern | A: adapter + prerender | B: separate Worker | C: `run_worker_first` entry |
| --- | --- | --- | --- |
| Static build and `dist` layout | Changes to `dist/client` + `dist/server` | Unchanged | Unchanged |
| `check:csp`, lychee, serve scripts | Need path edits (verified for `check:csp`) | Unchanged | Unchanged |
| `compatibility_date` vs build | Build prerenders in workerd: date must be supported (verified failure) | Only the API Worker | Only `wrangler dev` and deploy |
| Bindings and types | `wrangler.jsonc`, `wrangler types`, `import { env } from "cloudflare:workers"` | In the API Worker's own config | Same `wrangler.jsonc`; `wrangler types` |
| Page-level dynamic HTML | Yes (`prerender = false`, server islands) | No (JSON, fetched from the client) | Only by hand (`HTMLRewriter` or custom render) |
| Server islands | Yes | No | No |
| CSP on dynamic responses | Per response in code; `Astro.csp` API for HTML | Per response in code | Per response in code |
| Preview behavior | Previews need their own bindings; generated config mirrors `SESSION` and `IMAGES` | Two Previews to wire | One Preview; bindings per `previews` block |
| Free-plan blast radius | Only non-asset requests invoke the Worker | Only API requests | Only matched patterns (all requests if `true`) |
| Extra maintenance | Adapter version tied to the Astro major | Second deploy unit | Hand-written Worker entry |

## Caching dynamic responses

- Static assets: the repo sets immutable caching for `/_astro/*`; HTML defaults to `public, max-age=0, must-revalidate` with an ETag **(verified)**.
- On-demand pages: Astro documents setting `Cache-Control` on `Astro.response.headers` ("only available at the page level"), and Astro 7 adds an `Astro.cache` API (`set`, `invalidate`, tags, SWR) that requires a cache provider; `enabled` is false without one and in dev (API reference). Whether a provider exists for the Cloudflare adapter was not found (the route-caching guide URL I tried returned 404).
- Workers Cache API (`caches.default`): works on custom domains ("Workers deployed to custom domains have access to functional `cache` operations"); the docs do not explicitly say whether it works on `workers.dev`, so Preview URLs may not exercise caching. It is per data center, `delete()` purges only the local data center, it does not support `stale-while-revalidate`, and responses with `Set-Cookie` are not cached (https://developers.cloudflare.com/workers/runtime-apis/cache/). Server islands' GET URLs are cacheable with plain `Cache-Control`.
- Astro sessions use KV (eventually consistent, up to 60 seconds); relevant only if sessions stay on.

## Free-plan limits (Workers Free; https://developers.cloudflare.com/workers/platform/limits/ and per-product pricing pages)

- Static asset requests: "free and unlimited". Worker invocations (SSR, `run_worker_first` matches, API routes) are billed per Workers pricing and count against: 100,000 requests/day per account (resets 00:00 UTC; Error 1027 over the limit; routes can fail open or closed), 10 ms CPU per request, 50 subrequests, 128 MB memory, 64 MiB bundle uncompressed.
- KV: 100,000 reads/day, 1,000 writes/day, 1,000 deletes/day, 1,000 lists/day, 1 GB; operations fail once exceeded.
- D1: 5 million rows read/day, 100,000 rows written/day, 5 GB total; queries are rejected after a limit until reset.
- Workers AI: 10,000 Neurons/day; further operations fail on Free.
- Previews: 100 per Worker; Workers Builds: 3,000 build minutes/month (earlier research on #8).
- Implication: daily KV writes (1,000) and the 10 ms CPU cap are the tightest numbers; a write-heavy feature such as a counter hits KV first, while read-heavy usage fits easily. Server-side rendering React islands inside a Worker is the case to measure against 10 ms; prerendered pages avoid it.
